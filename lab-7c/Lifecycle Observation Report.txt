1. OVERVIEW & CONTROLS USED
--------------------------------------------------------------------------------
The project connects five distinct UIKit interactive controls to reactive state updates:
1. `UITextField`: Dynamic student name input with `.editingChanged` tracking.
2. `UISegmentedControl`: 4-segment Academic Year selector (Year 1 to Year 4).
3. `UISwitch`: Honors track program enrollment toggle.
4. `UISlider`: Continuous study hours per week slider (range: 5 to 40 hours) with live value readout.
5. `UIDatePicker`: Compact enrollment calendar picker.
6. `UIButton`: Triggers push navigation to `LifecycleDetailViewController` to observe stack transitions.

Whenever any control emits a touch or value event (`.valueChanged` or `.editingChanged`), the 
central `updateSummaryPanel()` method runs, reformatting all active state parameters into 
the live summary card.

3. EXPLANATION: viewDidLoad() VS viewWillAppear() (TASK 4)
--------------------------------------------------------------------------------
A. Which setup belongs in `viewDidLoad()`?
- `viewDidLoad()` is invoked strictly ONCE in the lifetime of a view controller, right after its view 
  hierarchy has been instantiated into memory from code or storyboard.
- Proper work for `viewDidLoad()`:
  1. Creating and configuring view elements (labels, buttons, sliders, text fields).
  2. Installing Auto Layout constraints (`NSLayoutConstraint.activate(...)`).
  3. Setting up delegates and data sources (`tableView.delegate = self`).
  4. Registering notification observers (`NotificationCenter.default.addObserver(...)`).
  5. One-time data model allocations and dependency bindings.
- Anti-pattern: Fetching fast-changing live sensor data or re-running layout code here on every screen return, 
  because `viewDidLoad()` will NOT execute when a user pops back to this screen from a child screen.

B. Which refresh belongs in `viewWillAppear()`?
- `viewWillAppear()` is called EVERY time right before the view becomes visible on screen (both on initial 
  presentation and whenever child screens are popped).
- Proper work for `viewWillAppear()`:
  1. Refreshing dynamic data that may have been edited in a child view controller (e.g. updating profile details).
  2. Refreshing timestamps, counters, badges, or unread message counts.
  3. Updating status bar style or navigation bar appearance customizations specific to this screen.
  4. Starting lightweight animations or reloading table view data to reflect state modifications.
- Anti-pattern: Re-adding subviews or re-creating constraints in `viewWillAppear()`, which results in duplicate 
  views, memory bloat, and conflicting constraint crashes.

4. KEYBOARD PRESENTATION & DISMISSAL LAYOUT CHECK (TASK 5)
--------------------------------------------------------------------------------
- Observers: Registered for `keyboardWillShowNotification` and `keyboardWillHideNotification`.
- Execution:
  * When keyboard shows: Calculates `keyboardFrame.height - safeAreaInsets.bottom + 16` and adjusts 
    `scrollView.contentInset.bottom` and `verticalScrollIndicatorInsets.bottom`.
  * Console Output: "⌨️ Keyboard appeared — Content inset adjusted by 301.0pt to preserve layout visibility."
  * When keyboard hides: Smoothly resets `contentInset.bottom = 0`.
- Result: Active text fields and summary panel remain fully visible and scrollable above the keyboard.
